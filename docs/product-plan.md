## 1. 背景与定位

- **现状**：数据模型与业务骨架已完成，UI 初版 demo 可运行。技术不是瓶颈。
- **问题**：市场上记账产品很多，做一个「大而全」的记账工具没有意义。
- **定位**：不做功能堆叠的账簿工具，而是**把「记账这个动作代表的意义」做得更好**——无论从 UE 上，还是从定义上。
- **产品逻辑 > 角色画像**：不把核心定位放在「谁在用」（年龄 / 收入），而放在「产品运行在什么逻辑上」。

## 2. 核心洞察

### 2.1 记账的负向螺旋

> **记录要付出成本，回看才有价值；而放弃记账的人，恰恰是在「记录成本」这一点上崩掉的。**

记录成本高 → 坚持不了 → 数据断裂 → 回看没价值 → 更不想记 → 弃用。
大而全工具的解法是「加更多功能」，但成本没降、意义没变强，照样被弃用。

### 2.2 度量 vs 动机

| 逻辑 | 优点 | 缺陷 |
| --- | --- | --- |
| 收入支出（度量） | 严谨、可信、可算 | 「持续记」没有回报 → 缺持续性 |
| 行为 / 目标（动机） | 有吸引力、想打开 | 难准确度量 → 容易虚、自欺 |

**这不是二选一，是两层。** 好的产品 = 严谨的度量底座 + 吸引人的意义层，两层靠「**派生**」缝合——意义必须**从真实账目实时算出来**，不能脱离账目自嗨（纯打卡 / 纯游戏化就是自欺，这也是「难度量」的根源）。

## 3. 分层模型

```
┌─ 意义层（目标投票）── 从账目实时派生 → 想回来
├─ 度量底座（觉察）── 低摩擦记录 + 回补 → 数据完整
└─ 缝合：记账动作 = 向目标投票
```

- **觉察是底座**：必须清楚「钱去哪了」，目标投票才有意义。
- **目标投票是意义层**：每记一笔，目标进度立即变化。
- **主次**：回补是地基（保证持续），意义层是核心（保证想用）。

## 4. 核心机制：目标 = 聚合投影

### 4.1 定义

> **目标 =（类目集合 × 时间窗 × 阈值 / 基准）**，进度 = 自动对账目求和。
> **用户永远不需要判断某笔是否「计划内」。**

「少花」不靠反事实（无法知道「本来会花多少」），改用**基准对比**：环比 / 前 N 月均值。可度量、来自真实账目。

| 目标（用户语言） | 系统翻译 | 怎么度量 |
| --- | --- | --- |
| 少喝奶茶 | 分类 ∈ {奶茶咖啡} 短窗 | 计数 or 求和 vs 基准 |
| 本周外卖 ≤ 200 | 分类 = 外卖 本周 | 求和 vs 阈值 |
| 攒 2000 | 收入 − 支出 ≥ ¥2000 | 净流入 |
| 零花费日 | 某天确认无支出 | 按天确认 |

### 4.2 时间粒度：短窗优先

这是 v0.4 的核心修正。**目标的价值取决于反馈速度和信息增量**，两者都要求窗口足够短。

- **短窗（今天 / 本周）是激励层，月度只做结算。** 「本月外卖 ≤ 800」记一笔 30 元只让进度动 3.75%，且用户本来就知道自己超没超——信息增量接近零。
- **目标必须可直接计数。** 「第 4 次外卖」「已经 6 天没点外卖」是能被立刻感知的量；百分比不能。
- **只做用户自己算不清的目标。** 这是筛选器：用户数得出来的事不值得做成目标（信息增量仍为零）。

### 4.3 目标类型优先级

| 优先级 | 类型 | 例 | 为什么 |
| --- | --- | --- | --- |
| P0 | **零花费日 / 计数型** | 「这周 3 天没花钱」「本月奶茶 ≤ 4 次」 | 短窗、可计数、不打开 App 就不知道 |
| P1 | 阈值型 | 「本周外卖 ≤ 200」 | 直观，但反馈慢，适合做短窗 |
| P2 | 净流入型 | 「这个月攒 2000」 | 需要完整数据才准，依赖覆盖率 |

**注**：零花费日成立的前提是「今天没花钱」这个显式动作存在（见 §5.5）——否则系统无法区分「没花钱」和「忘了记」。

## 5. 记录层面

### 5.1 分类 = 生活维度（用户可见，只有一层）

- 分类粗而**有生活意义**：外卖 / 奶茶咖啡 / 买菜做饭 / 交通 / 娱乐 / 社交人情……而不是「早饭胡辣汤」这类细标签。
- **每个分类都对应一个「生活上说得清的问题」**，而不是财务口径。
- 用户面前的分类**只有一层、数量少（10 个以内）、一屏放得下**——这是两键记录的成本上限。
- 具体分类表见 [dev-plan.md](dev-plan.md) M0-2。

### 5.2 内部维度（用户不可见）

用户面前是一层分类，但叙事需要跨分类的横切视角。**不用分类树，用 2–3 个正交维度**：

| 维度 | 取值 | 支撑的叙事 |
| --- | --- | --- |
| 饮食方式 | 自制 / 外食 | 「做饭 8 天 vs 外卖 12 次」 |
| 场景 | 独处 / 社交 | 「人情支出占比」 |
| 性质 | 必需 / 享受 | 「享受 vs 生存的构成」 |

- **性质是标签不是分类**：互不排斥，可叠加。
- **用户永远不选、也看不到**，只在回看里看到结论。
- 由分类 + 备注 + 时间 + 金额 + 商户自动推断。
- 一条标签错了只是轻微偏差，不会像分类错了那样让整张统计失真。
- 这层维度**同时也是「自动归类」的收敛目标**——没有它，模型归到哪儿都行，什么都算不出来。

### 5.3 自动归类的边界

> **钱由用户在记录时确认；归类由后台自动完成。**

- **金额：记录时确认，一次，不可自动化。** 这一秒是「投票」本身。若连金额都自动抓取，产品退化成账本，意义层没有主语。
- **归类：后台自动**，事后可改，每周给一次「这批归得对吗」的轻确认（30 秒，一次，不是每笔）。
- **红线**：不得静默替用户决定「这笔钱花了」——AI 只降低捕捉成本，不消灭觉察（见 §9.3）。

### 5.4 两键记录 + 自动带值

- **自动带出常用金额**：该分类最近一次 / 众数金额。分类少而稳定 → 带值几乎百发百中。
- 流程：**点分类 → 金额已带出 → 确认**。
- 这是「记录成本趋近于零」的落点，也是觉察底座得以持续的原因。
- **入口不止在 App 内**：锁屏、小组件、分享面板、快捷指令 / App Intents 都应能发起同一次记录。若必须先打开 App，入口之争已经输了一半。

### 5.5 弱精确与诚实性机制

弱精确不是口号，必须有机制承接，否则「数据不完整 → 意义层说谎 → 信任崩塌」，比没有产品更糟。

| 机制 | 做法 | 解决什么 |
| --- | --- | --- |
| **约金额** | 允许记 `≈30`，而不是被迫打 28.5 | 用户在「记不准」和「不记」之间不再选后者 |
| **数据覆盖率** | 按天统计有记录的天数；所有结论都要能说「基于 X 天」 | 让产品知道自己不知道什么 |
| **今天没花钱** | 一键确认当天无支出，锁屏 / 通知可达 | 让「零花费日」可判定；把「没消费的日子」变成可动作的一天 |

- 覆盖率不是加分项，是**回看的前提**：一句「本月外卖 12 次」如果没有覆盖率背书，就是假话。
- 精确度要求会让人因为「没记准」而干脆不记；放宽即拆掉「怕记错」的放弃开关。
- 不引入对账、差额核查类功能——流程刻意粗糙而轻松。

### 5.6 「冲动了」轻量标签

可选、成本低、事后可改，作为零成本的轻量行为信号。用可选类型存储（nil = 未标记），避免历史数据被当成「不冲动」。

## 6. 数据来源：语义自持

> **数据只能由用户自己产生，但不必在当时产生。**

- **不做第三方账单导入**（支付宝 / 微信 / 银行账单）。理由：外部账单是**财务口径**，会污染建立在**生活维度**上的语义体系；且无法保证符合本产品的场景定义。
- **保留回补**（手输 / 截图 / 语音）。回补的是用户自己的记忆，语义仍是用户自己的。手动回补**免费、不限次数、零摩擦**。
- **时间必须拆成两个字段**：`date`（钱花在哪天）与 `createdAt`（哪天录进来）。覆盖率、叙事、目标求和**一律按 date**。
- **回补逐笔确认**，批量卡片一张一张过、每张可改，不做一键入库。
- **补记不惩罚**：补记不清零任何记录、不产生「失败」文案（见 §8）。

**推论**：产品本质是「每天和用户确认一次的节奏产品」，不是分析工具。

## 7. 回看 = 生活叙事

### 7.1 三种节奏

| 节奏 | 载体 | 目的 |
| --- | --- | --- |
| 日 | 「今天没花钱」一键确认 | 让无消费的日子也能动作 |
| 周 | 一句话 | 提供「我一直在」的连续性，成本极低 |
| 月 | 那封信 | 讲这个月的生活，不报表 |

### 7.2 首屏那句话（生死线）

**首屏不是图表，是一句「懂你」的话。** 它是唯一的留存引擎——用户回来是因为那句话让他觉得值，不是因为怕断。

三个要素（缺一不可）：

1. **数字是关于你的，而且是你记不住的**（「第 12 次」「3 个月没做到」）
2. **有人格在说话**，不是系统通知
3. **有连续性**——它记得上周的你

句式：**事实 + 一个对比 + 一句轻判断或提问**。

- 「这周你没点外卖。上次做到是 3 个月前。」
- 「本月奶茶 11 杯，比上月多 3 杯——但每杯便宜了 2 块。」
- 「你有 4 天没记。攒钱目标按已记的部分算，还差 620。」

三条硬规则：

1. **数字必须确定性计算**，LLM 只负责组织说法。算错一次，信任归零。
2. **每句话都能下钻**到具体账单，回答「凭什么是这句」。
3. **必须包含一个用户不知道的事实**。复述用户已知的（「你这个月花了 5000」）是废句，宁可不发。

**载体**：首屏 + 锁屏。点通知直接落在这句话上，不需要进 App、不需要点按钮。看一眼就走也没关系。

### 7.3 生活维度叙事

回看讲「生活」，不讲「报表」：

- 这个月自己做饭 X 天 vs 外卖 Y 次（饮食结构）
- 「冲动了」的次数与占比
- 享受 vs 生存的构成
- 目标进度 + 基准反馈（「本月点了 12 次外卖，比上月少 5 次，省了 ¥180」）

维度由 §5.2 的内部标签支撑，用户看不到标签本身。

## 8. 留存机制

### 8.1 原则：保留损失厌恶，消除悬崖

**损失厌恶是重要的留存杠杆，要用。** 要拆掉的不是它，是「断一次就归零」的结构。

病根有两层：

1. **沉没成本一次性归零**：断一天损失的不是 1 天，是前 20 天。理性反应是放弃。
2. **更隐蔽：会诱导造假**。为了不断，用户会补假账，或继续点但不记。数据一旦污染，意义层就在撒谎——比流失更严重。

| 结构 | 断一天的后果 | 用户实际行为 |
| --- | --- | --- |
| 归零 | 前 20 天全废 | 放弃，或造假 |
| 冻结 / 券 | 消耗一张券 | 开始做资源管理，多一层成本 |
| **边际（采用）** | 少 1 天，补上就恢复 | 补记，继续 |

### 8.2 计量单位：周

「偶尔缺个别」是常态，所以**不用「天」当计量单位**：

> 「这周你记了 3 天。」

一周 7 次机会，缺一天没有任何后果，**只有整周全空才算洞**。损失厌恶照样在（你不想这周是 0），但没有悬崖，也不需要任何货币或冻结机制。

参数：本周有 ≥1 天记录即算在场（待确认是否要求 ≥3 天）。

### 8.3 三层指标

| 层 | 指标 | 性质 |
| --- | --- | --- |
| 主 | **数据完整度**：「本月记录 18 天 / 账本覆盖 87%」 | 累积、**边际损失**、补记可修复 |
| 辅 | **连续天数**：「本月最长连续 12 天」 | 只展示，**不设门槛、不绑定任何权益、断了不清零** |
| 内容 | 一句话回看 | 给予式触发，负责「想回来」 |

**硬约束：连续天数不能兑换任何东西。** 一旦它变成解锁条件、额度来源、权益门槛，断一次就会连带损失权益，惩罚翻倍。

**补记可修复完整度**，这就是「偶尔缺个别」的零成本解法：漏了补上，洞就填了。不需要货币，不需要用户做任何管理。

### 8.4 文案主语

把主语从用户换到系统：

- 不写：「你已 3 天未记录」——这是过失
- 改写：「这 3 天我还没有你的记录」——这是缺口

**默认假设用户只是忘了，而不是没做到。** 这与「海绵替你收着」的人格是同一个。

### 8.5 挂起项：回补额度券

曾考虑「每日记录 → 获得补记额度 → 次月过期 → 补记时消耗」。挂起原因：

- 额度限制的是**最需要鼓励的行为**（回补），摩擦加错了位置；
- 过期是纯损失厌恶，且会让用户在「现在记还是以后补」上开始算计，反而提高记录成本；
- 会让「漏记」被合法化。

保留的替代方向：若将来需要月度节奏感，做成会员侧的**AI 解析配额**（加速器），不做「补记许可」。

## 9. 语音与 AI

### 9.1 AI native 的含义：结构迁就用户

传统记账是「用户迁就结构」（填表单输入、看表格输出）。AI native 反过来：

- **输入**：从「填表」变成「倾倒素材」——截图、语音、一段粘贴，App 负责结构化。
- **输出**：从「报表」变成「对话 + 叙事」。

### 9.2 四个值得 AI 的时刻

| 时刻 | AI 做什么 | 本地 / 云 |
| --- | --- | --- |
| **回补**（最大杠杆） | 截图 / 粘贴 / 语音 → 结构化账单，逐笔确认 | 本地（Vision OCR + 解析） |
| 回看叙事 | 月度「信」，把数字讲成生活故事 | 云 LLM（低频、高价值） |
| 自然语言问答 | 「这个月外卖花超了吗」→ 一句话 | 云 LLM / 本地规则兜底 |
| 目标建议 | 「按历史，外卖定 800 比较现实」 | 本地统计即可 |

### 9.3 AI 的边界

> **AI 降低「捕捉成本」，但不消灭「觉察」与「能动性」。**

- **AI 做草稿，用户做确认**（human-in-the-loop）。而**那一次确认就是投票**。
- 金额确认不可自动化；归类可以自动化（§5.3）。
- **AI 是外设，不是内核**：解析器、叙事、问答都应可替换。明天模型强十倍，产品应该变强，而不是被替代。

### 9.4 与通用 AI agent 的差异化

| 维度 | 通用 chat agent | 本产品 |
| --- | --- | --- |
| 状态 | 会话级，记不住三个月前 | 长期、结构化、本机驻留 |
| 计算 | 生成式，会算错 | 确定性聚合，金额永不出错 |
| 在场 | 你去找它（pull） | 花钱现场就在（ambient） |
| 信任 | 幻觉，无法核对 | 每句话可回溯到具体账单 |
| 输出 | 对话 | 对话 + 可被外部 agent 调用的结构化数据 |

三条推论：

1. **凡是「一次对话就能完美解决」的需求，都不做成功能。**
2. **护城河押在状态与确定性，不押在模态。** 语音 / 截图入口会被平台迅速抹平；账本 + 派生指标 + 纵向历史抹不平。
3. **不做围墙花园。** 主动让账本可被查询（导出、快捷指令、App Intents），成为通用 agent 的「记忆层」，而不是它的竞品。

**关于输入模态**：记账的高频动作不是「输入」，是「确认」。语音能把 30 秒压到 10 秒，但那一次确认仍然要做；**如果那一次确认没有价值，模态再先进也没用。** 因此：

- 语音：不做「对着 App 说话」，做「事后一口气补」+ 系统级 Siri / App Intents。
- 图片：截图 / 小票解析，护城河浅，但极适合做首次 aha。
- 视频：不做。真正的复合形态是「边说边拍」，不必为模态而模态。

## 10. 品牌叙事（待拍板）

把「吸收」和「塑造」看成对立，是因为把**人格**当成了**机制**：

- **吸收是姿态**：不评判、不漏、不催你。这是人格。
- **塑造是机制**：目标与聚合。这是产品。

所以不是二选一：**海绵是那个替你收着的人，用户是那个在塑造的人。**

对外方向：「它替你记着，你只管变。」

> 尚未拍板。若最终选择「吸收」为主调，§9.3 的 AI 边界需要重写（被动记录会削弱「投票」的主动性）。

## 11. 商业模式

### 11.1 模型：免费核心 + 订阅会员

理由：独立开发者养不起一次性收入下的 AI 持续成本；免费用户零服务器成本（本地 + CloudKit），免费档可以大方。

### 11.2 切分

| 免费（核心，本地） | 会员 |
| --- | --- |
| 两键记录 + 自动带值 | 多设备云端同步（CloudKit） |
| 生活维度分类 + 内部标签推断 | AI 月度叙事（完整版「信」） |
| 回看 + 基础叙事（**一句话月报**） | 自然语言问答 |
| 基础目标（聚合投影 + 基准反馈） | **AI 回补配额**（截图 / 语音批量解析） |
| 手动回补（不限次数） | 深度报告 / 高级生活维度 |

### 11.3 两条修正

1. **AI 回补改为配额制**：免费版每月给少量次数（如 3 次），保证首次 aha 不被付费墙挡住；付费买的是**量**和**深度**，不是「许可」。手动回补永远免费无限。
2. **免费版必须有一件可记住的产物**：一句话月报。否则免费用户体验不到「意义」，转化无从谈起。

### 11.4 定价（区间参考）

- 包月：¥12–18（主力档）
- 包年：¥68–98（锚点档，约按月价 60–70%）
- 不做 7 天档：周期过短易被理解为诱导，且与「不制造压力」的气质不符。

### 11.5 与隐私定位的关系

「免费也能用，数据默认只在你手机里；会员只是同步 + 解读，不是把数据卖给服务器。」与「海绵吸水式本地保存」自洽。

## 12. 目标用户（弱画像，待定）

- 不用角色做核心定位。若需要一个锚点，倾向：帮「想攒下第一笔钱」的人，把攒钱从愿望变成看得见的进度。

## 13. 产品原则（v0.4）

1. 记录成本趋近于零；不要求精确到每一笔（弱精确），但**必须诚实**（约金额 + 覆盖率）。
2. 觉察是底座：数据要完整可靠（回补支撑）；产品必须知道自己不知道什么。
3. 目标 = 向往而非约束；用聚合投影 + 基准反馈，**短窗优先、可计数**，不做每笔「计划内」判断。
4. 分类 = 生活维度；回看讲「生活」不讲「报表」。**分类不承担情感，情感由首屏那句话承担。**
5. 不做大而全；每个功能都要回答「服务于哪个痛点」。
6. 产品语言 > 报表语言：叙事、进度、故事。
7. **AI 做草稿，用户做确认**；AI 降低捕捉成本，不消灭觉察与能动性。金额确认不可自动化。
8. **核心本地功能免费**；AI / 同步等持续成本进会员；付费买深度与数量，不买许可。
9. **语义自持**：数据只由用户产生，不导入第三方账单口径。
10. **保留损失厌恶，消除悬崖**：一次中断不得让此前积累作废；绝不使用清零、倒计时、红色警告、「你已 N 天未记」。
11. **状态与确定性是护城河**，不是模态；不做围墙花园，让账本可被外部 agent 调用。
12. **只用描述句和邀请句**：给事实贴标签就是审判，产品不做审判。

## 14. 明确不做

| 不做 | 原因 |
| --- | --- |
| 第三方账单导入（支付宝 / 微信 / 银行） | 财务口径污染生活维度语义 |
| 断一次归零的连续打卡 | 诱导放弃与造假 |
| 用连续天数兑换额度 / 权益 / 勋章 | 断一次惩罚翻倍 |
| 每日补记额度券 | 给最需要鼓励的行为加摩擦（挂起，非否决） |
| 倒计时 / 「还剩 X 天」 | 催促句 |
| 红色超支警告 / 「已超支」文案 | 评判句 |
| 「你已 N 天未记录」 | 把缺口写成过失 |
| 排行 / 社交攀比 | 外部评价，与觉察无关 |
| 通用规则引擎 / 目标 DSL | 过度设计；类型写死枚举 |
| 视频录入 | 为模态而模态 |
| 「对着 App 说一句话记账」 | 场景尴尬、比两键慢 |

## 16. 与技术的关系

- **数据层已够用**：Transaction / Category / Budget + 按分类、时段统计。
- **预算本质就是「类目 × 月份」的聚合投影雏形**，技术路线已踩一半；但目标需要短窗与计数型，需扩展 §4.3 的类型。
- **需扩展**：
  - 目标语义类型（零花费日 / 计数 / 阈值 / 净流入）
  - 短窗聚合与基准查询（服务层）
  - 常用金额联想（按分类最近 / 众数）
  - 内部标签维度与推断
  - 约金额、覆盖率、「今天没花钱」的模型与统计
  - 回补流程（含批量、逐笔确认）
  - 回看页（生活维度叙事）
  - 云端同步 + 会员鉴权
  - AI 分层（本地 OCR / 启发式 + 云 LLM）
- **建议节奏**：产品定义（本文）→ 数据与入口 → 目标与回看 → 最小闭环 → 再扩展。详细排期见 dev-plan。
