## 1. 背景与定位

- **现状**：数据模型与业务骨架已完成，UI 初版 demo 可运行。技术不是瓶颈。
- **问题**：市场上记账产品很多，做一个「大而全」的记账工具没有意义。
- **定位**：不做功能堆叠的账簿工具，而是**把「记账这个动作代表的意义」做得更好**——无论从 UE 上，还是从定义上。
- **产品逻辑 > 角色画像**：不把核心定位放在「谁在用」（年龄 / 收入），而放在「产品运行在什么逻辑上」。

## 2. 核心洞察

### 2.1 记账的负向螺旋

> **记录要付出成本，回看才有价值；而放弃记账的人，恰恰是在「记录成本」这一点上崩掉的。**

记录成本高 → 坚持不了 → 数据断裂 → 回看没价值 → 更不想记 → 弃用。
大而全工具的解法是「加更多功能」，但成本没降、意义没变强，照样被弃用。

### 2.2 度量 vs 动机

| 逻辑 | 优点 | 缺陷 |
| --- | --- | --- |
| 收入支出（度量） | 严谨、可信、可算 | 「持续记」没有回报 → 缺持续性 |
| 行为 / 目标（动机） | 有吸引力、想打开 | 难准确度量 → 容易虚、自欺 |

**这不是二选一，是两层。** 好的产品 = 严谨的度量底座 + 吸引人的意义层，两层靠「**派生**」缝合——意义必须**从真实账目实时算出来**，不能脱离账目自嗨（纯打卡 / 纯游戏化就是自欺，这也是「难度量」的根源）。

## 3. 分层模型

```
┌─ 意义层（目标投票）── 从账目实时派生 → 想回来
├─ 度量底座（觉察）── 低摩擦记录 + 回补 → 数据完整
└─ 缝合：记账动作 = 向目标投票
```

- **觉察是底座**：必须清楚「钱去哪了」，目标投票才有意义。
- **目标投票是意义层**：每记一笔，目标进度立即变化。
- **主次**：回补是地基（保证持续），意义层是核心（保证想用）。

## 4. 核心机制：目标 = 聚合投影

### 4.1 定义

> **目标 =（类目集合 × 时间窗 × 阈值 / 基准）**，进度 = 自动对账目求和。
> **用户永远不需要判断某笔是否「计划内」。**

「少花」不靠反事实（无法知道「本来会花多少」），改用**基准对比**：环比 / 前 N 月均值。可度量、来自真实账目。

| 目标（用户语言） | 系统翻译 | 怎么度量 |
| --- | --- | --- |
| 少喝奶茶 | 分类 ∈ {奶茶咖啡} 短窗 | 计数 or 求和 vs 基准 |
| 本周外卖 ≤ 200 | 分类 = 外卖 本周 | 求和 vs 阈值 |
| 攒 2000 | 收入 − 支出 ≥ ¥2000 | 净流入 |
| 零花费日 | 某天确认无支出 | 按天确认 |

### 4.2 时间粒度：短窗优先

这是 v0.4 的核心修正。**目标的价值取决于反馈速度和信息增量**，两者都要求窗口足够短。

- **短窗（今天 / 本周）是激励层，月度只做结算。** 「本月外卖 ≤ 800」记一笔 30 元只让进度动 3.75%，且用户本来就知道自己超没超——信息增量接近零。
- **目标必须可直接计数。** 「第 4 次外卖」「已经 6 天没点外卖」是能被立刻感知的量；百分比不能。
- **只做用户自己算不清的目标。** 这是筛选器：用户数得出来的事不值得做成目标（信息增量仍为零）。

### 4.3 目标类型优先级

| 优先级 | 类型 | 例 | 为什么 |
| --- | --- | --- | --- |
| P0 | **零花费日 / 计数型** | 「这周 3 天没花钱」「本月奶茶 ≤ 4 次」 | 短窗、可计数、不打开 App 就不知道 |
| P1 | 阈值型 | 「本周外卖 ≤ 200」 | 直观，但反馈慢，适合做短窗 |
| P2 | 净流入型 | 「这个月攒 2000」 | 需要完整数据才准，依赖覆盖率 |

**注**：零花费日成立的前提是「今天没花钱」这个显式动作存在（见 §5.6）——否则系统无法区分「没花钱」和「忘了记」。

## 5. 记录层面

### 5.1 三层结构

用户看到的只有一维：**动作**。领域和性质都在内部，用户不可见。

| 层 | 内容 | 用户可见 | 谁在用 |
| --- | --- | --- | --- |
| **记录层** | 动作 / 场景，一屏、一层、10 个左右 | 是，唯一的可见维度 | 两键记录 |
| **聚合层** | 领域：吃 / 住 / 行 / 用 / 玩 / 人情 / 健康 | 否，从动作 1:1 映射 | 「这个月吃饭花了 X」 |
| **横切层** | 自制 / 外食、独处 / 社交、必需 / 享受 | 否，自动推断 | 生活叙事 |

**为什么要分三层**：一个分类名如果同时承担「记录时的检索标签」和「回看时的价值判断」，就必然出现情感互斥——「娱乐」「购物」是回看的词，「买菜做饭」「点外卖」是记录的词。放进同一个网格，等于一个在描述动作、一个在给行为分类。

分开之后，每个词只背一个职责：

- 记录层的唯一标准是「用户 0.5 秒内能把自己刚才做的事对上号」。
- **情感不由分类承担，由首屏那句话承担**（§7.2）。
- 每多一维，每次记录就多一次决策；决策就是成本。

### 5.2 记录层：动作分类

规则：全部是「我做了什么」，2–3 字，口语，不用财务词，不用评价词。

| 分类 | 内部领域 | 包含 | 不包含 |
| --- | --- | --- | --- |
| 买菜做饭 | 吃 | 食材、调料、厨房用品 | 熟食外带 |
| 点外卖 | 吃 | 送到家 / 公司的 | 自取堂食 |
| 下馆子 | 吃 | 坐着吃的，含快餐堂食 | 给别人买的 |
| 咖啡奶茶 | 吃 | 饮品，含便利店咖啡 | 正餐 |
| 出行 | 行 | 地铁、公交、打车、加油、停车 | 长途旅行 |
| 住 | 住 | 房租、水电、物业、维修 | 家具家电 |
| 买东西 | 用 | 非食物的实物 | 送礼 |
| 玩 | 玩 | 票、演出、游戏、会员、订阅 | 吃喝 |
| 人情 | 人情 | 送礼、请客、随礼、红包 | 给家人的日常开销 |
| 健康 | 健康 | 看病、买药、健身、体检 | 保健品 |
| 其他 | — | 兜底 | — |

11 个，4×3 网格一屏放得下。

**食物占 4 个是刻意的不对称**：吃是唯一真正需要细分的领域（饮食结构是核心叙事），其他领域粗一点没有损失。

**边界规则**（比名字更重要——用户犹豫「这算哪个」的那两秒，就是成本）：

1. **为别人花的钱一律记人情**，不管花在哪。自己吃才记下馆子。
2. **人情是对外的社交成本，不是对家人的支出**：送礼、红包、随礼才记人情；给家人日常买的记买东西。
3. **一趟买回来的东西，按「主要目的」记一个分类，不拆分。** 买菜为主就全记买菜。拆分会让记录变成整理工作，与弱精确冲突。

### 5.3 聚合层与横切层

**聚合层（领域）**：吃 / 住 / 行 / 用 / 玩 / 人情 / 健康 / 其他。由 §5.2 的分类 1:1 映射，只用于聚合展示，不做用户选择。

**横切层（正交标签，可叠加）**：

| 维度 | 取值 | 支撑的叙事 |
| --- | --- | --- |
| 饮食方式 | 自制 / 外食 | 「做饭 8 天 vs 外卖 12 次」 |
| 场景 | 独处 / 社交 | 「人情支出占比」 |
| 性质 | 必需 / 享受 | 「享受 vs 生存的构成」 |

- **是标签不是分类**：互不排斥，可叠加。
- **用户永远不选、也看不到**，只在回看里看到结论。
- 由分类 + 备注 + 时间 + 金额 + 商户自动推断。
- 一条标签错了只是轻微偏差，不会像分类错了那样让整张统计失真。
- 这层维度**同时也是「自动归类」的收敛目标**——没有它，模型归到哪儿都行，什么都算不出来。

### 5.4 自动归类的边界

> **钱由用户在记录时确认；归类由后台自动完成。**

- **金额：记录时确认，一次，不可自动化。** 这一秒是「投票」本身。若连金额都自动抓取，产品退化成账本，意义层没有主语。
- **归类：后台自动**，事后可改，每周给一次「这批归得对吗」的轻确认（30 秒，一次，不是每笔）。
- **红线**：不得静默替用户决定「这笔钱花了」——AI 只降低捕捉成本，不消灭觉察（见 §9.3）。

### 5.5 两键记录：把输入变成选择

> **输入是任务，选择是确认。而这个产品里，「确认」就是投票。**

#### 字段逐项

| 字段 | 形态 |
| --- | --- |
| 分类 | 选择（按使用频率排序） |
| 金额 | **选择**（众数 / 档位） |
| 日期 | **选择**（今天 / 昨天 / 更早） |
| 账户 | **无操作**（默认上次；只有一个账户时不显示） |
| 冲动 | 开关 |
| 备注 / 内容 | 输入（唯一开放的字段，且可选） |

**整条动线里，用户唯一可能需要「打」的是备注，而备注是可选的。** 产品不要求用户输入任何东西，只要求选择和确认。

这同时是应对「用户已习惯多模态对话」的答案：不必在输入上竞争，因为这个产品不比输入。

#### 自适应金额输入

众数预填的命中率是**分类金额方差的函数**。在买菜这类高方差分类上预填历史值，会诱发锚定偏差——用户看一眼就确认，数据被污染。所以策略必须随方差变化：

| 分类特征 | 策略 | 点击 |
| --- | --- | --- |
| 咖啡奶茶 / 点外卖（高频、低方差） | 众数预填 | 1 |
| 出行（双峰：地铁 / 打车） | 最近值 + 两个常用档 | 1 |
| 买菜做饭（高频、高方差） | 档位：P25 / P50 / P75 / P90 | 1 |
| 住（低频、极低方差） | 众数 | 1 |
| 买东西（中低频、高方差） | 手输 | 4–6 |

判定按该分类历史金额的**变异系数（CV）**：

- CV < 0.15 且样本 ≥ 3 → 众数预填
- CV 0.15–0.5 → 最近 3 笔中位数 + 两个常用档
- CV > 0.5 → 纯档位，**不从历史预填**

约束：

- **不得在高方差分类上预填历史值**（污染源，不是加速器）。
- 档位不写死，取该分类历史分位数，随物价与习惯自动漂移。
- **单档位占比 > 60% 视为档位设计不合格**：用户被迫选近似值，数据实际已丢失，需加档或退回手输。
- 选档位 = 记录档位代表值，并**自动标记为估计值**（与 §5.6 的约金额机制合并，用户无需额外操作）。

**结果：真正需要打字的只剩低频分类，四个高频分类全部一次点击完成。**

#### 精度分层

- 目标：**超过用户的记忆误差即可**。人对自己的月支出通常只能估到 ±10–20%，稳定做到 ±10% 就会觉得「它比我记得清楚」。
- **结构准确优先于金额准确**：把房租记成「买东西」比把 132 记成 100 严重得多——前者让整月叙事失真，后者只偏 3%。
- 因此投入优先级是「分类命中率 > 金额精度」。带值的意义是少一步，不是更准。
- 验证口径：用户看到「本月支出 ¥4,860」时，是否会说「差不多就是这个数」。

### 5.6 弱精确与诚实性机制

弱精确不是口号，必须有机制承接，否则「数据不完整 → 意义层说谎 → 信任崩塌」，比没有产品更糟。

| 机制 | 做法 | 解决什么 |
| --- | --- | --- |
| **约金额** | 不提供小数点；输入区一律显示「≈30」。列表与汇总不加 ≈，避免满屏免责声明 | 用户在「记不准」和「不记」之间不再选后者 |
| **数据覆盖率** | 按天统计有记录的天数；所有结论都要能说「基于 X 天」 | 让产品知道自己不知道什么 |
| **今天没花钱** | 一键确认当天无支出，锁屏 / 通知可达 | 让「零花费日」可判定；把没消费的日子变成可动作的一天 |

- 覆盖率不是加分项，是**回看的前提**：一句「本月外卖 12 次」如果没有覆盖率背书，就是假话。
- 精确度要求会让人因为「没记准」而干脆不记；放宽即拆掉「怕记错」的放弃开关。
- 不引入对账、差额核查类功能——流程刻意粗糙而轻松。

### 5.7 「冲动了」轻量标签

可选、成本低、事后可改，作为零成本的轻量行为信号。用可选类型存储（nil = 未标记），避免历史数据被当成「不冲动」。

### 5.8 消费内容（记忆层）

**内容不是「记录」的一部分，是「记忆」的一部分。**

#### 价值不在金额，在重复性

> 「这个月你点了 14 次外卖，其中 9 次是同一家。」

这句话指向的是**习惯**，不是花费。觉察的深层含义是：不是知道花了多少，是知道自己在重复什么。

**验证标准**：如果不能生成这类句子，内容就只是日记，不该进产品。

#### 性质：软失败

| | 缺失后果 | 要求 |
| --- | --- | --- |
| 金额 | 求和错、目标错，整个产品撒谎 | 必须有，必须确认 |
| 内容 | 句子变粗（「外卖 12 次」而不是「9 次是同一家」） | 有则更好 |

约束：**10 次记录里 7 次没写内容，产品必须照常成立。** 不能出现在必填位置，不能有「还有 3 笔没写内容」的提示，不能影响任何统计。一旦变成义务，就违反了两键记录的第一原则。

#### 时机：回看时补，不在记录时补

回看时用户才有动机——他看到「外卖 12 次」才想知道是哪 12 次，而且那时能对着截图回忆。记录的那一刻，他只想快点记完走人。

- **快路径（两键）不碰内容。** 不要把语音塞进记录流程：语音比两键慢，会破坏节奏。
- **回看页提供「补一句」入口**，语境触发，成本最低。
- **回补时天然带上**（支付截图里本来就有商户名）。

#### 来源可靠性

支付截图 / 小票（高：商户 + 金额 + 时间齐全）> 语音（中：中文店名易错）> 打字（不主推）。

#### 结构化：原文 + 派生两层

| 层 | 内容 | 可见性 | 出错后果 |
| --- | --- | --- | --- |
| 原文 | 用户说的话（「杨国福麻辣烫」） | 可见、可搜索 | 无 |
| 派生 | 商户归一 + 品项标签 | **不可见** | 轻微偏差，只影响叙事精度 |

与分类的处理方式一致：用户层简单、内部层自动、错误可容忍。**绝不让「商户归一」变成用户的活。**

#### 三个风险

1. **隐私升级**：内容比金额更敏感（买了什么药、去了哪家酒店）。默认本地；若走云 LLM，只传聚合结果，不传原文。
2. **气质滑向消费日记**：内容会让产品有温度，也会让用户觉得「要写清楚吃了什么」。UI 必须反复声明它是可选的，空着不显示任何提示。
3. **商户数据会诱导你做推荐**：「你常去这家，附近有优惠」是电商逻辑，一旦沾上，「觉察」的立场就没了。见 §14。

#### 排期

不单独做，**跟着回补（M4）一起落地**：M2 保持 note 自由文本，不要求、不提示；回补落地时由 OCR 顺带填 merchant，同时上线「同一家 N 次」这类叙事；语音只用于回补场景的批量口述。

### 5.9 积累与护城河

**产品最深的资产不是模型，是用户的选择历史。**

#### 不是技术护城河，是时间护城河

众数、分位数、频率排序技术上零门槛。壁垒在于「用户已经用了 8 个月」：换 App 就归零，第一周又回到每次改两下。

- 竞品能复制功能，复制不了用户的时间。
- 大模型再强，也不知道你每天中午点的是 28 块那家。
- 切换成本随使用时长增长——这是唯一会自己长大的资产。

#### 三层积累

| 层 | 积累什么 | 复制难度 |
| --- | --- | --- |
| 金额默认 | 这个分类通常多少钱 | 低 |
| 分类习惯 | 我把生活分成哪几块、边界在哪 | 中 |
| 生活结构 | 通勤远、外卖多、储蓄率 12%、周末才花钱 | 高 |

第一层决定快不快，第三层决定离不开。

#### 顺序：留存 → 积累 → 护城河

护城河只在留存成立之后存在。若用户三周就走，护城河为零。不能指望「积累」去创造留存，这决定了资源顺序：先把前 30 天做对，再谈护城河。

#### 前 30 天最脆弱：爬坡曲线

| 时间 | 用户感受 |
| --- | --- |
| 第 1 天 | 手动选金额（还不信你） |
| 第 3 次记同一分类 | 金额已经对了（第一次「它懂我」） |
| 第 1 周末 | 首屏那句话说出他自己没注意到的事 |
| 第 2 周 | 发现记账从三步变成一步（速度是可感知的变聪明） |

**核心指标：首次命中率**——用户第一次点某分类时，预填金额被直接确认（未修改）的比例。它从 0 爬到 60% 的速度，就是产品变成护城河的速度。

#### 数据质量是地基

如果数据脏（大量估计值、覆盖率低、分类乱放），积累越快，错得越系统化——积累出来的不是「更懂你」，是「更自信地误解你」。

所以 §5.6 的诚实性机制不是道德设计，是护城河的地基。没有它，时间积累是负资产。

#### 同步是积累的保险

换手机丢掉一年的默认值，护城河瞬间变人质。**CloudKit 同步因此不是锦上添花，而是资产保全**，优先级跟随留存验证。

#### 与开放的关系

不做围墙花园：数据可导出、可被外部 agent 调用。这不削弱护城河——被带走的是历史，带不走的是「越用越快」的能力，对手仍要从零积累用户的习惯。

## 6. 数据来源：语义自持

> **数据只能由用户自己产生，但不必在当时产生。**

- **不做第三方账单导入**（支付宝 / 微信 / 银行账单）。理由：外部账单是**财务口径**，会污染建立在**生活维度**上的语义体系；且无法保证符合本产品的场景定义。
- **保留回补**（手输 / 截图 / 语音）。回补的是用户自己的记忆，语义仍是用户自己的。手动回补**免费、不限次数、零摩擦**。
- **时间必须拆成两个字段**：`date`（钱花在哪天）与 `createdAt`（哪天录进来）。覆盖率、叙事、目标求和**一律按 date**。
- **回补逐笔确认**，批量卡片一张一张过、每张可改，不做一键入库。
- **补记不惩罚**：补记不清零任何记录、不产生「失败」文案（见 §8）。

**推论**：产品本质是「每天和用户确认一次的节奏产品」，不是分析工具。

## 7. 回看 = 生活叙事

### 7.1 三种节奏

| 节奏 | 载体 | 目的 |
| --- | --- | --- |
| 日 | 「今天没花钱」一键确认 | 让无消费的日子也能动作 |
| 周 | 一句话 | 提供「我一直在」的连续性，成本极低 |
| 月 | 那封信 | 讲这个月的生活，不报表 |

### 7.2 首屏那句话（生死线）

**首屏不是图表，是一句「懂你」的话。** 它是唯一的留存引擎——用户回来是因为那句话让他觉得值，不是因为怕断。

三个要素（缺一不可）：

1. **数字是关于你的，而且是你记不住的**（「第 12 次」「3 个月没做到」）
2. **有人格在说话**，不是系统通知
3. **有连续性**——它记得上周的你

句式：**事实 + 一个对比 + 一句轻判断或提问**。

- 「这周你没点外卖。上次做到是 3 个月前。」
- 「本月奶茶 11 杯，比上月多 3 杯——但每杯便宜了 2 块。」
- 「你有 4 天没记。攒钱目标按已记的部分算，还差 620。」

三条硬规则：

1. **数字必须确定性计算**，LLM 只负责组织说法。算错一次，信任归零。
2. **每句话都能下钻**到具体账单，回答「凭什么是这句」。
3. **必须包含一个用户不知道的事实**。复述用户已知的（「你这个月花了 5000」）是废句，宁可不发。

**载体**：首屏 + 锁屏。点通知直接落在这句话上，不需要进 App、不需要点按钮。看一眼就走也没关系。

### 7.3 生活维度叙事

回看讲「生活」，不讲「报表」：

- 这个月自己做饭 X 天 vs 外卖 Y 次（饮食结构）
- 「冲动了」的次数与占比
- 享受 vs 生存的构成
- 目标进度 + 基准反馈（「本月点了 12 次外卖，比上月少 5 次，省了 ¥180」）

维度由 §5.3 的内部标签支撑，用户看不到标签本身。

## 8. 留存机制

### 8.1 原则：保留损失厌恶，消除悬崖

**损失厌恶是重要的留存杠杆，要用。** 要拆掉的不是它，是「断一次就归零」的结构。

病根有两层：

1. **沉没成本一次性归零**：断一天损失的不是 1 天，是前 20 天。理性反应是放弃。
2. **更隐蔽：会诱导造假**。为了不断，用户会补假账，或继续点但不记。数据一旦污染，意义层就在撒谎——比流失更严重。

| 结构 | 断一天的后果 | 用户实际行为 |
| --- | --- | --- |
| 归零 | 前 20 天全废 | 放弃，或造假 |
| 冻结 / 券 | 消耗一张券 | 开始做资源管理，多一层成本 |
| **边际（采用）** | 少 1 天，补上就恢复 | 补记，继续 |

### 8.2 计量单位：周

「偶尔缺个别」是常态，所以**不用「天」当计量单位**：

> 「这周你记了 3 天。」

一周 7 次机会，缺一天没有任何后果，**只有整周全空才算洞**。损失厌恶照样在（你不想这周是 0），但没有悬崖，也不需要任何货币或冻结机制。

参数：本周有 ≥1 天记录即算在场（待确认是否要求 ≥3 天）。

### 8.3 三层指标

| 层 | 指标 | 性质 |
| --- | --- | --- |
| 主 | **数据完整度**：「本月记录 18 天 / 账本覆盖 87%」 | 累积、**边际损失**、补记可修复 |
| 辅 | **连续天数**：「本月最长连续 12 天」 | 只展示，**不设门槛、不绑定任何权益、断了不清零** |
| 内容 | 一句话回看 | 给予式触发，负责「想回来」 |

**硬约束：连续天数不能兑换任何东西。** 一旦它变成解锁条件、额度来源、权益门槛，断一次就会连带损失权益，惩罚翻倍。

**补记可修复完整度**，这就是「偶尔缺个别」的零成本解法：漏了补上，洞就填了。不需要货币，不需要用户做任何管理。

### 8.4 文案主语

把主语从用户换到系统：

- 不写：「你已 3 天未记录」——这是过失
- 改写：「这 3 天我还没有你的记录」——这是缺口

**默认假设用户只是忘了，而不是没做到。** 这与「海绵替你收着」的人格是同一个。

### 8.5 挂起项：回补额度券

曾考虑「每日记录 → 获得补记额度 → 次月过期 → 补记时消耗」。挂起原因：

- 额度限制的是**最需要鼓励的行为**（回补），摩擦加错了位置；
- 过期是纯损失厌恶，且会让用户在「现在记还是以后补」上开始算计，反而提高记录成本；
- 会让「漏记」被合法化。

保留的替代方向：若将来需要月度节奏感，做成会员侧的**AI 解析配额**（加速器），不做「补记许可」。

## 9. 语音与 AI

### 9.1 AI native 的含义：结构迁就用户

传统记账是「用户迁就结构」（填表单输入、看表格输出）。AI native 反过来：

- **输入**：从「填表」变成「倾倒素材」——截图、语音、一段粘贴，App 负责结构化。
- **输出**：从「报表」变成「对话 + 叙事」。

### 9.2 四个值得 AI 的时刻

| 时刻 | AI 做什么 | 本地 / 云 |
| --- | --- | --- |
| **回补**（最大杠杆） | 截图 / 粘贴 / 语音 → 结构化账单，逐笔确认 | **云端多模态**（本地只保留确认与降级路径） |
| 回看叙事 | 月度「信」，把数字讲成生活故事 | 云 LLM（低频、高价值） |
| 自然语言问答 | 「这个月外卖花超了吗」→ 一句话 | 云 LLM / 本地规则兜底 |
| 目标建议 | 「按历史，外卖定 800 比较现实」 | 本地统计即可 |

### 9.3 AI 的边界

> **AI 降低「捕捉成本」，但不消灭「觉察」与「能动性」。**

- **AI 做草稿，用户做确认**（human-in-the-loop）。而**那一次确认就是投票**。
- 金额确认不可自动化；归类可以自动化（§5.4）。
- **AI 是外设，不是内核**：解析器、叙事、问答都应可替换。明天模型强十倍，产品应该变强，而不是被替代。

### 9.4 与通用 AI agent 的差异化

| 维度 | 通用 chat agent | 本产品 |
| --- | --- | --- |
| 状态 | 会话级，记不住三个月前 | 长期、结构化、本机驻留 |
| 计算 | 生成式，会算错 | 确定性聚合，金额永不出错 |
| 在场 | 你去找它（pull） | 花钱现场就在（ambient） |
| 信任 | 幻觉，无法核对 | 每句话可回溯到具体账单 |
| 输出 | 对话 | 对话 + 可被外部 agent 调用的结构化数据 |

三条推论：

1. **凡是「一次对话就能完美解决」的需求，都不做成功能。**
2. **护城河押在状态与确定性，不押在模态。** 语音 / 截图入口会被平台迅速抹平；账本 + 派生指标 + 纵向历史抹不平。
3. **不做围墙花园。** 主动让账本可被查询（导出、快捷指令、App Intents），成为通用 agent 的「记忆层」，而不是它的竞品。

**关于输入模态**：记账的高频动作不是「输入」，是「确认」。语音能把 30 秒压到 10 秒，但那一次确认仍然要做；**如果那一次确认没有价值，模态再先进也没用。** 因此：

- 语音：不做「对着 App 说话」，做「事后一口气补」+ 系统级 Siri / App Intents。
- 图片：截图 / 小票解析，护城河浅，但极适合做首次 aha。
- 视频：不做。真正的复合形态是「边说边拍」，不必为模态而模态。

### 9.5 本地与云的分工

| 能力 | 位置 | 原因 |
| --- | --- | --- |
| 账本、聚合、目标、覆盖率、首屏那句话的数字 | **本地，确定性计算** | 金额不能算错；状态是资产 |
| 截图 / 语音解析 | **云端多模态** | 本地规则覆盖不了多模态输入与语义纠错（断句、同音字、数字归一） |
| 月度叙事、自然语言问答 | 云端 LLM | 低频、高价值 |

**为什么回补不走本地**：语音批量的断句、店名同音纠错、数字归一（「一百二」是 120 还是 102）都依赖语言理解；小票这类非规整输入会让规则库的维护成本随模板数量线性增长。规则解析「越用越贵」，LLM「越用越便宜」。

**硬约束**：

1. **API key 只能在服务端**，客户端只调自己的转发层（否则一抓包就被白嫖）。
2. **请求不留存**：不写日志、不进训练，只回传结构化字段。
3. **离线可用**：解析不可用时，手动记录必须完全可用。
4. **可关闭**：用户可选择只发送文字、或不使用 AI 解析。
5. **云端只做「理解」，不做「记忆」和「计算」。**

隐私叙事随之改写为：「**数据存在本地；解析是一次性的、不留存。**」比「全本地」弱，但诚实——而诚实是这个产品的底色。

## 10. 品牌叙事（待拍板）

把「吸收」和「塑造」看成对立，是因为把**人格**当成了**机制**：

- **吸收是姿态**：不评判、不漏、不催你。这是人格。
- **塑造是机制**：目标与聚合。这是产品。

所以不是二选一：**海绵是那个替你收着的人，用户是那个在塑造的人。**

对外方向：「它替你记着，你只管变。」

> 尚未拍板。若最终选择「吸收」为主调，§9.3 的 AI 边界需要重写（被动记录会削弱「投票」的主动性）。

## 11. 商业模式

### 11.1 模型：免费核心 + 订阅会员

理由：独立开发者养不起一次性收入下的 AI 持续成本；免费用户零服务器成本（本地 + CloudKit），免费档可以大方。

### 11.2 切分

| 免费（核心，本地） | 会员 |
| --- | --- |
| 两键记录 + 自动带值 | 多设备云端同步（CloudKit） |
| 生活维度分类 + 内部标签推断 | AI 月度叙事（完整版「信」） |
| 回看 + 基础叙事（**一句话月报**） | 自然语言问答 |
| 基础目标（聚合投影 + 基准反馈） | **AI 回补配额**（截图 / 语音批量解析） |
| 手动回补（不限次数） | 深度报告 / 高级生活维度 |

### 11.3 两条修正

1. **AI 回补改为配额制**：免费版每月给少量次数（如 3 次），保证首次 aha 不被付费墙挡住；付费买的是**量**和**深度**，不是「许可」。手动回补永远免费无限。
2. **免费版必须有一件可记住的产物**：一句话月报。否则免费用户体验不到「意义」，转化无从谈起。
3. **分层解析**：免费用户走本地规则 / 端侧模型（零边际成本），会员走云端多模态（受限额度）。这样 aha 不被付费墙挡住，也不为所有人生成 Token 账单。

### 11.4 定价（区间参考）

- 包月：¥12–18（主力档）
- 包年：¥68–98（锚点档，约按月价 60–70%）
- 不做 7 天档：周期过短易被理解为诱导，且与「不制造压力」的气质不符。

### 11.5 与隐私定位的关系

「免费也能用，数据默认只在你手机里；会员只是同步 + 解读，不是把数据卖给服务器。」与「海绵吸水式本地保存」自洽。

## 12. 目标用户（弱画像，待定）

- 不用角色做核心定位。若需要一个锚点，倾向：帮「想攒下第一笔钱」的人，把攒钱从愿望变成看得见的进度。

## 13. 产品原则（v0.6）

1. 记录成本趋近于零；不要求精确到每一笔（弱精确），但**必须诚实**（约金额 + 覆盖率）。
2. 觉察是底座：数据要完整可靠（回补支撑）；产品必须知道自己不知道什么。
3. 目标 = 向往而非约束；用聚合投影 + 基准反馈，**短窗优先、可计数**，不做每笔「计划内」判断。
4. 分类 = 生活维度；回看讲「生活」不讲「报表」。**分类不承担情感，情感由首屏那句话承担。**
5. 不做大而全；每个功能都要回答「服务于哪个痛点」。
6. 产品语言 > 报表语言：叙事、进度、故事。
7. **AI 做草稿，用户做确认**；AI 降低捕捉成本，不消灭觉察与能动性。金额确认不可自动化。
8. **核心本地功能免费**；AI / 同步等持续成本进会员；付费买深度与数量，不买许可。
9. **语义自持**：数据只由用户产生，不导入第三方账单口径。
10. **保留损失厌恶，消除悬崖**：一次中断不得让此前积累作废；绝不使用清零、倒计时、红色警告、「你已 N 天未记」。
11. **状态与确定性是护城河**，不是模态；不做围墙花园，让账本可被外部 agent 调用。
12. **只用描述句和邀请句**：给事实贴标签就是审判，产品不做审判。
13. **选择优先于输入**：能选择就不要输入。输入是任务，选择是确认。
14. **积累是护城河**：数据质量优先于功能数量；宁可不记，不可记错。

## 14. 明确不做

| 不做 | 原因 |
| --- | --- |
| 第三方账单导入（支付宝 / 微信 / 银行） | 财务口径污染生活维度语义 |
| 断一次归零的连续打卡 | 诱导放弃与造假 |
| 用连续天数兑换额度 / 权益 / 勋章 | 断一次惩罚翻倍 |
| 每日补记额度券 | 给最需要鼓励的行为加摩擦（挂起，非否决） |
| 倒计时 / 「还剩 X 天」 | 催促句 |
| 红色超支警告 / 「已超支」文案 | 评判句 |
| 「你已 N 天未记录」 | 把缺口写成过失 |
| 排行 / 社交攀比 | 外部评价，与觉察无关 |
| 通用规则引擎 / 目标 DSL | 过度设计；类型写死枚举 |
| 视频录入 | 为模态而模态 |
| 基于商户的推荐 / 优惠 / 定向营销 | 电商逻辑，会毁掉「觉察」的立场 |
| 分账 / AA / 报销 | 细节控需求，不在目标人群内 |
| 多币种 / 汇率 | 同上 |
| 信用卡 / 花呗 / 负债管理 | 会把「记账」变成「管账」，目标用户不需要；账户维度只保留一个默认账户 |
| 导出给会计 / 对账报表 | 与弱精确、精度分层冲突 |
| 「对着 App 说一句话记账」 | 场景尴尬、比两键慢 |

## 15. 待决策

1. **品牌叙事**：吸收 / 塑造，或按 §10 的「人格 + 机制」双轨收。
2. **周判定阈值**：本周 ≥1 天算在场，还是 ≥3 天。
3. **目标首发类型**：零花费日 / 计数型 / 阈值型，先做哪一个（§4.3 建议 P0 起）。
4. **首屏那句话的生成方式**：纯模板，还是模板 + LLM 润色（M2 前必须定）。
5. **免费用量**：AI 回补每月免费次数。
6. **服务端形态**：纯转发，还是转发 + 鉴权 + 计量（建议后者，反正都要建）。
7. **解析默认是否传原图**：传图更准，传文字更隐私。
8. **分类最终表**：已在 product-plan §5.2 定稿，落地细节见 dev-plan M0-2。

## 16. 与技术的关系

- **数据层已够用**：Transaction / Category / Budget + 按分类、时段统计。
- **预算本质就是「类目 × 月份」的聚合投影雏形**，技术路线已踩一半；但目标需要短窗与计数型，需扩展 §4.3 的类型。
- **需扩展**：
  - 目标语义类型（零花费日 / 计数 / 阈值 / 净流入）
  - 短窗聚合与基准查询（服务层）
  - 自适应金额（众数 / 中位数 + 档位 / 纯档位，按变异系数判定）
  - 内部标签维度与推断
  - 约金额、覆盖率、「今天没花钱」的模型与统计
  - 回补流程（含批量、逐笔确认）
  - 回看页（生活维度叙事）
  - 云端同步 + 会员鉴权
  - 共享账本（两人共同记录）——不是多账户，需要单独设计，优先级低于同步
  - 云端解析（多模态）+ 本地降级路径
  - 最小服务端（鉴权 / 计量 / 转发）
- **建议节奏**：产品定义（本文）→ 数据与入口 → 目标与回看 → 最小闭环 → 再扩展。详细排期见 dev-plan。
