# Spendge 开发计划

> 状态：**M1 进行中**（M0 基本完成，M2 已落地） · 最后更新：2026-11-12
>
> 上游文档：[product-plan.md](product-plan.md)（产品方向 v0.3）、[architecture.md](architecture.md)（当前技术设计）。
> 本文只回答一个问题：**按什么顺序把产品方案落到代码里**。不重复论证产品方向；方向有疑问回 product-plan。

## 0. 现状基线

| 层次 | 现状 | 结论 |
| --- | --- | --- |
| 数据模型 | Account / Category / Transaction / Budget / DayConfirmation 齐全，Category 带 code + domain，金额存 Int64 分 | 可用，缺 Goal 与 merchant |
| 服务层 | Transaction / Account / Category / Budget / Insight / DayConfirmation / VoiceParser 齐全 | 基本收口；仅 `BudgetService.setBudget` 与 `TransactionService.update` 没有调用方 |
| UI 层 | 三页：设置 · 今天 · 回看；记录页为整页选择式（分类竖列 + 常驻键盘 + 连续记账） | 可用，缺「编辑一笔」与「预算入口」 |
| 工程 | 无 test target；DEBUG 启动跑 SelfCheck（30 项）；编译需 DEVELOPER_DIR 指向 Xcode.app | 回归靠 SelfCheck，属技术债 |

已知断点（2026-11-12 复核）：

1. 没有预算设置入口 → 回看页只有存在预算时才显示预算区，Release 下等于不存在。
2. 不能编辑一笔 → `TransactionService.update` 无调用方，记错只能删了重记。
3. 没有数据导出 → 本机是唯一副本，换机或误删即丢。
4. 没有 test target → 回归依赖手动跑 SelfCheck。

## 2. M0：地基收口

**目标**：不加任何用户可见的新功能，把三件「越晚做越贵」的事一次做完。

### M0-1 文档同步

- 提交 docs/product-plan.md（当前未跟踪）。
- 更新 README：删掉「UI/UE 待讨论」的过时表述，改为指向三份文档。
- 本文件与 architecture.md 互链。

### M0-2 分类体系重构（最高优先级）

产品方案 §5.1–5.3 把分类定为三层（记录层动作 / 聚合层领域 / 横切层标签），当前 DefaultData.swift 是会计科目式（餐饮 / 交通 / 购物 / 居住…），必须换掉，否则后面所有回看口径都建在错的维度上。

**改动内容**

1. Category 增加 `code: String?`（稳定标识）与 `domain: String`（内部聚合领域）。此后代码里**一律不按 name 匹配分类**。
2. 种子分类按 product-plan §5.2 定型：**用户只见动作，领域在内部**。

   | code | 名称 | 内部领域 |
   | --- | --- | --- |
   | `takeout` | 点外卖 | 吃 |
   | `dineout` | 下馆子 | 吃 |
   | `grocery` | 买菜食材 | 吃 |
   | `drink` | 奶咖茶饮 | 吃 |
   | `snack` | 零食水果 | 吃 |
   | `daily` | 生活日用 | 用 |
   | `wear` | 衣帽鞋袜 | 用 |
   | `gear` | 装备器材 | 用 |
   | `appliance` | 家具家电 | 住 |
   | `health` | 医疗保健 | 健康 |
   | `housing` | 房租水电 | 住 |
   | `outing` | 出行游玩 | 行 |
   | `subscription` | 订阅话费 | — |
   | `social` | 人情往来 | 人情 |
   | `other_expense` | 其他 | — |

   > 三段分组：吃吃喝喝 / 居家与穿戴 / 住行与账单；sortOrder 按 1x / 2x / 3x 分段落，段间画短横线。

   > 旧 `transport` + `fun` 迁移到 `outing`，旧 `shopping` 迁移到 `gear`；迁移函数保留已有账单，不删库。

   收入侧保持精简：工资 / 兼职 / 理财 / 其他收入，同样加 code。**收入侧内部领域暂不定，先保持原始记录。**

3. **删除 DemoData.swift**：试用阶段不再自动写入模拟账单，避免污染真实数据。需要演示时再单独加。
4. 迁移：**不做迁移**。开发期数据、UI、UE 都允许推倒重来——DEBUG 下按种子版本（UserDefaults）清空重建，Release 不触发。
5. 顺带定文案口径：统计页按内部领域聚合（吃 / 行 / 住…），M2 起再改为生活叙事，本阶段文案先不动。

**验收**：全新安装后分类为 11 个动作词、每个都带 code 与 domain，网格一屏放得下（4×3）；模拟账单落在正确分类；全仓 grep 不到按 name 匹配分类的代码。

### M0-3 测试基线

采用最轻的形式，**不新建 test target**：`Services/SelfCheck.swift`（#if DEBUG）用内存容器跑核心不变量，启动时打印结果。

- 覆盖：种子完整性（11 支出分类 / 全部有 code / 吃的领域 4 个）、记账与月度汇总、余额联动、预算进度、删除保护、删除分类后置空且仍计入总额、按 code 取分类。
- 失败只在控制台打印 `[SelfCheck] FAIL: ...`，不阻断运行；用户手动试用时也能顺带看到。
- 取舍：没有 `xcodebuild test` 的自动化入口，靠启动自检兜底。等数据层稳定、需要跑 CI 时再升级成独立 target。

**验收**：xcodebuild test 全绿；故意改错一处汇总逻辑时有用例失败。

### M0-4 服务层收口

- StatisticsView 改用 TransactionService.summary，删掉 View 内的重复聚合。
- @Query 带月份区间 Predicate（`[start, end)`），不再全表拉取后在内存过滤。
- UI 层禁止 `try?` 吞异常：加一个轻量错误提示（banner / toast），保存与删除失败要可见。
- AccountService.totalAssetsCents 去掉 N+1（当前每个账户各拉一次全量账单）。

**验收**：StatisticsView 不再出现 Dictionary(grouping:) 这类聚合代码；人为制造保存失败时用户能看到提示。

**本阶段不做**：任何新功能、Goal、回看改版、CloudKit。

**状态（2026-11-12）**：M0-2 分类体系重构已完成；M0-4 服务层基本收口（只剩 setBudget / update 没有调用方）；M0-3 测试基线**未做**，暂由 app 内 SelfCheck（30 项）顶替；M0-1 文档同步部分完成。

## 4. M2：核心机制

**目标**：把「记录成本趋近于零」和「回看讲生活不讲报表」落到代码，这是产品唯一的差异化落点。

**状态：已落地（2026-11-12 复核）**。落地时相对原方案的差异：

- 分类从「4×3 网格」改为**左列竖向标签 + 右侧数字键盘**，一屏可滚；
- 日期改为**固定 7 天轴**，不做「今天 / 昨天 / 更早」；
- 金额支持**一位小数与千分位**，上限 7 位整数，字号按宽度自适应；
- 语音输入已实现（原计划放在 M4），解析在端侧，带本地关键词规则；
- 记下后**不关闭页面**，顶部提示并清空，便于连续记账；
- 验收里的「首次命中率」尚未埋点。

### M2-1 选择型记录

RecordView 从表单改为「选择 + 确认」，全程不出现键盘（备注除外）：

- 首屏 = 分类网格（11 个动作词，4×3 一屏）+ 金额已预填 + 一个大确认键。
- 日期改为选择（今天 / 昨天 / 更早），不用 DatePicker。
- 账户默认上次使用；只有一个账户时**不显示**。
- 备注 / 冲动开关折进「更多」，默认折叠。
- 保存后回到原页并保留分类选中，便于连续记账。

### M2-2 ~~自适应金额输入~~ 已改为「最近金额快填」

原方案用变异系数分档（众数预填 / 中位数 + 档位 / 纯档位），实测后下线（2026-11-13）：

- 触发门槛是「同一分类 ≥ 3 笔」，15 个分类摊下来几乎永远不触发；
- 用户真实输入以键盘和语音为主，省下的一次点击抵不上理解成本；
- 金额重复只集中在房租 / 话费 / 订阅这类固定项，用「猜」解决重复是错位的。

现在（`TransactionService.recentAmounts()`）：

- 键盘上方常驻**最近 3 个不同金额**，全分类共享，点一下即填；
- 不做任何统计推断，也不预填——只记忆用户真的输过的数字；
- 固定项的重复留给后续的**周期账单**，那才是「每月一样」的正解。

附带影响：`isApproximateAmount` 字段一并移除（没有读方，也没必要留）；`AmountSuggestion` 整个类型删除。

### M2-3 ~~冲动标签~~ 已取消

试用后删除（product-plan §5.7）：它既不降低记录成本，也不产生用户看得懂的结论。字段已从模型移除。

### M2-4 生活维度回看

统计页改造，从「分类占比报表」改为生活叙事：

- 外卖 / 下馆子 / 奶咖茶饮的次数（外食结构，只数记录过的次数）
- 本周 vs 上周同类对比（先做最简单的环比，基准体系在 M3 展开）
- 目标进度卡预留位置，M3 填充

### M2-5 诚实性机制

对应 product-plan §5.5，三件事一起做：

- ~~**约金额**~~：已移除（2026-11-13，字段没有读方；输入区仍显示 ≈ 作为语气，不落库）。
- **数据覆盖率**：按天统计「有记录或已确认无支出」的天数，回看页所有结论都要带「基于 X 天」。
- **今天没花钱**：新增 DayConfirmation 实体，一键确认当天无支出。**这是零花费日目标与覆盖率的数据源，缺了它两者都不成立。**

**验收**：记一笔 ≤ 2 次点击；连记 5 笔不需要碰键盘；四个高频分类（外卖 / 奶咖 / 买菜 / 出行）都能一次点击完成；回看页能生成一句「本月外卖 12 次，比上月少 5 次」；未记满整月时该句必须带「基于 X 天」；点「今天没花钱」后当天覆盖率 +1。

**观测指标（本地统计，不上传）**：首次命中率——用户第一次点某分类时，预填金额被直接确认（未修改）的比例。M2 结束时要求它随使用次数单调上升。

**本阶段不做**：语音输入、截图识别、云 LLM 叙事（M4）。

## 5. M3：意义层

**目标**：实现「目标 = 聚合投影」，记账动作变成向目标投票。

### M3-1 Goal 模型

```swift
@Model
final class Goal {
    var id: UUID
    var title: String              // 用户语言，如「少喝奶茶」
    var kindRawValue: String       // zeroSpendDays / countTarget / categorySum / netInflow
    var categoryIDs: [UUID]        // 聚合范围（categorySum 用）
    var periodRawValue: String     // month / rolling30
    var targetCents: Int64?        // 阈值型目标（如 ≤ 800）
    var basisRawValue: String      // fixed / previousMonth / trailing3Avg
    var isActive: Bool
    var createdAt: Date
    var updatedAt: Date
}
```

三种类型写死枚举即可，**不做通用规则引擎 / DSL**——这是最容易被过度设计的地方。

### M3-2 聚合与进度

- `TransactionService.categorySum(categoryIDs:from:to:)`、`netInflow(from:to:)`、`zeroSpendDays(from:to:)`
- `GoalService.progress(for:asOf:)` → 当前值 / 目标值 / 基准值 / 是否达标
- 基准：fixed（直接用 target）、previousMonth（环比）、trailing3Avg（前 3 月均值）

### M3-3 目标向导

把「少喝奶茶」翻译成「drink 分类 + 前 3 月均值作为基准」。纯本地统计，不引入 LLM。

### M3-4 Budget 的处置

Budget 保留为「月度总额上限」这一种特殊 Goal，暂不与 Goal 合并。等 Goal 稳定、真实使用一段时间后再决定是否统一，避免现在就做一次大迁移。

### M3-5 目标投票

记一笔后目标进度立即变化；进度卡必须**可解释**（说明用了哪个区间、哪条聚合），否则用户不信。

**验收**：设定「本周 3 天不点外卖」，记一笔外卖后目标卡立即变化，显示「本周 2 / 3 天」；设定「本月奶茶 ≤ 4 次」，显示「第 3 杯」而不是百分比。短窗计数型目标的反馈必须是可数的。

## 6. M4：后续（只留位，不排期）

顺序：**手动批量回补** → 云端多模态解析 → **CloudKit 同步** → 云 LLM 月度叙事 → StoreKit 订阅。

> 调整（2026-11-12）：数据导出已提前到 M1-7；同步放在回补之后，因为回补会先改变数据结构（source / merchant），先把数据形态定下来再上同步，避免迁移两次。

回补改为云端多模态解析（product-plan §9.2 / §9.5）：需要一个最小服务端做鉴权、计量与转发，API key 不得进客户端。解析请求不留存，并保留「仅发送文字」的降级开关。

### M4-1 账号与同步（CloudKit）

**不做独立账号体系**：不注册、不要手机号、不要邮箱密码。身份就是用户的 Apple ID；未登录也能完整使用，登录只是为了同步。设置页里的「账号」是一张 iCloud 状态卡，不是注册表单。

设置页要承载的同步相关项：

| 项 | 行为 |
| --- | --- |
| iCloud 同步 | 开关；关闭后仅本机保存，并提示「其它设备不会再更新」 |
| 仅 Wi-Fi 同步 | 默认开启，移动网络下排队等待 |
| 上次同步 | 时间 + 结果（成功 / 失败原因），失败可点重试 |
| 立即同步 | 手动触发一次，给出进行中状态 |
| 账号状态 | 显示 iCloud 是否可用、容量不足等系统级阻塞原因 |

实现约定：

1. 开启 iCloud capability 与 CloudKit 容器，SwiftData 用 `ModelConfiguration(cloudKitDatabase:)`。
2. **无账号 / iCloud 不可用时自动降级为纯本地**，不阻塞任何记录动作。
3. 冲突策略：最后写入优先 + 删除墓碑；冲突不允许静默丢数据。
4. **危险操作单独一屏**（关闭同步、清空本机数据、删除 iCloud 数据），每个都要二次确认，并写清后果：删了不能恢复、影响哪些设备。
5. 订阅（StoreKit）与 iCloud 账号解耦：订阅状态跟着 Apple ID 走，不另建用户表。

回补落地时顺带完成消费内容（product-plan §5.8）：解析填 merchant、「同一家 N 次」叙事。记录流程本身不要求输入内容。

进入条件：M2 / M3 验证了「记账动作有意义」这个假设——没人因为目标进度而回来，后面这些都别做。

## 7. 跨阶段技术约定

1. **视图不 fetch 全表**：@Query 必须带日期区间或 fetchLimit；所有聚合走 Service。
2. **Service 返回快照 struct**（沿用 CategorySummary 的做法），不把 @Model 泄漏给新 View。
3. **UI 层不吞错误**：禁止裸 `try?`，改为可见提示。
4. **金额只走 Money**，任何地方不出现 Double 表示金额。
5. **新聚合必须配用例**，且覆盖空数据与边界月份。
6. **调试数据不自动写入**：启动只播种分类与账户，任何模拟数据都要显式开启。
7. **改数据模型必须同时更新 architecture.md 的 ER 图**
8. **默认值优先**：新字段尽量可选或带默认值，保证 SwiftData 轻量迁移能过。
9. **解析在云端，key 只在服务端**：客户端内置 key 等于公开密钥；请求不留存、不进日志。
10. **首屏与目标的数字必须本地确定性计算**，不经模型。云端只做「理解」。
