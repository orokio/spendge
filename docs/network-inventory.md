# 网络调用清单（客户端 ↔ 服务端 / 第三方）

> 目的：把客户端会发起的网络请求集中列出来，评估流量、频次与服务端压力。
> 现状基线：2026-11-24 · v1（本地 + iCloud + Bugly + 友盟 + 设备登记）

## 1. 总览

| 类别 | 谁发起 | 现状 | 备注 |
|---|---|---|---|
| 自建服务端 | 客户端 | 只有 `/v1/devices/register` | 地址为空时不发请求 |
| 崩溃上报 | Bugly SDK | 已接入 | 隐私同意后才启动 |
| 行为统计 | 友盟 SDK | 已接入 | 隐私同意后才启动 |
| 账本同步 | CloudKit | 待账号开通 | 不经过我们 |
| 内购 | StoreKit | 待账号开通 | 不经过我们 |
| 语音识别 | Speech 框架 | 已接入 | 默认走系统能力，我们不收音频 |

## 2. 自建服务端

| 接口 | 触发 | 频次 | 请求体 | 响应 | 状态 |
|---|---|---|---|---|---|
| `POST /v1/devices/register` | 启动（隐私同意后） | **每次启动一次**；失败下次重试 | ≈ 200 B | 200 OK，无内容 | v1 已有客户端 |
| `GET /health` | **不是客户端**：部署脚本与监控探活 | `serve.sh` 启动后轮询几次；线上监控若接入，按 30–60 秒一次 | — | `{status: ok}` | 已有骨架 |
| `POST /v1/parse` | 用户发起解析（M4） | 按使用量 | 图片 300 KB–1 MB / 文本 < 2 KB | 结构化结果 < 2 KB | 未开始 |
| `POST /v1/diagnostics` | 用户反馈或异常（M4） | 偶发 | 20–100 KB（仅动作与错误码） | 200 OK | 未开始 |

**压力判断**：v1 只有设备登记，DAU 1 万时每天也只有约 1 万次以内的请求，对单机 Flask（2 worker）没有压力。真正的瓶颈会出现在 `/v1/parse`：耗时主要花在模型调用，不在 Web 层。

## 3. 第三方 SDK

只记录**什么时候会用到**，不评估请求频率（频率由 SDK 内部控制，代码里改不了，也不作为我们的容量指标）。

| SDK | 域名（抓包可见） | 使用时机 | 数据内容 |
|---|---|---|---|
| Bugly | `ios.bugly.qq.com` | 用户同意隐私后初始化；崩溃发生时记录，之后补报 | 崩溃堆栈、App 版本、deviceId |
| 友盟 | `utoken.umeng.com`、`cnlogs.umeng.com`、`yumao.puata.info` | 用户同意隐私后初始化；9 个埋点事件产生时记录 | 事件名与属性（金额只到档位）、App 版本、deviceId |

说明：

- 两者都只在用户同意隐私政策后启动（`PrivacyConsent.canStartSDK`），拒绝即完全不启动
- Bugly 已按官方关闭 CPU、磁盘、内存、机型、系统版本等采集项，只剩崩溃所需的最小集
- 都走 HTTPS，不含金额原文、备注内容与账号信息

## 4. 系统能力（不属于我们的服务）

| 能力 | 流量 | 说明 |
|---|---|---|
| CloudKit 同步 | 首次全量 + 之后增量 | 由 Apple 承载；首次同步的数据量随账本大小增长，需在双设备验证时实测 |
| StoreKit | 极小的票据校验 | 购买/恢复时发生，由 Apple 处理 |
| Speech 语音识别 | 默认本机；不支持时可能走 Apple 服务 | 我们不接收、不存储音频 |

## 5. 流量估算（单设备）

| 场景 | 估算 |
|---|---|
| 冷启动（无同步、无解析） | 设备登记约 0.2 KB；第三方 SDK 的上报由其内部决定，不计入我们的容量 |
| 日常使用（每天 5 笔记录） | 我们自己的服务端无请求 |
| 首次开启 iCloud 同步 | 账本全量，随记录数增长（需实测） |
| 一次截图解析（M4） | 上行 300 KB–1 MB，下行 < 2 KB |

## 6. 服务端容量粗算（M4 参考）

假设：DAU 1 万，10% 使用解析，人均每天 2 次 → 2000 次/天 ≈ 0.03 QPS，峰值按 10 倍算 0.3 QPS。Web 层可以忽略；成本取决于模型 API 的单价与单次 token 数，需要在上线前用真实样本测一次。

## 7. 怎么测（建议固定流程）

1. **客户端抓包**：真机 + Proxyman/Charles，只看我们自己的域名（第三方 SDK 只确认“在不该发的时候没发”）
2. **Instruments Network 模板**：看总流量与连接数，确认没有异常重试或长连接
3. **服务端日志**：按接口记录 `deviceId`、耗时、状态码、请求体大小（不含内容）
4. **回归口径**：每次改网络相关代码后，跑一遍同样的三步，记录到本文的表格里

## 8. 风险与待确认

- 第三方 SDK 只关心“是否在隐私同意后才启动”，不跟踪其内部频率
- CloudKit 首次同步的流量与耗时未测，双设备验证时补数据
- 解析接口的图片压缩策略未定（直接影响流量与模型成本）
- 诊断日志需要上限（当前本地滚动 1 MB），上传前要截断
- 服务端地址为空时客户端不发任何请求，这条要作为回归项保留
